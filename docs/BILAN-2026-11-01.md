# Bilan complet du projet — 1 novembre 2026

> Guides actuels : [état actif](EXECUTION.md), [étapes restantes](PROCHAINES-ETAPES.md), [publication FTP](FTP-DEPLOYMENT.md). Ce document conserve son contexte et ses preuves historiques ; les lots CodeMirror/MySQLi plus récents sont décrits dans ces guides.

## Conclusion et périmètre

Le projet est un **prototype local fonctionnel et mesuré**, avec un vrai moteur PHP/MariaDB commun et une première interface structurée. Il n'est pas encore un environnement PHP généraliste ni un outil SQL au niveau de finition de phpMyAdmin. Aucun pourcentage global de réalisation n'est pertinent : un appel enregistré n'équivaut pas à une conformité complète et une compilation réussie n'équivaut pas à un produit terminé.

Code fonctionnel de référence au début de ce bilan : `5b0375c07a838d6a7036cd486bd86d0bb05f630a`. Dépôt de travail propre avant l'ajout du présent bilan ; les commits de développement sont locaux, sans push/merge confirmé. Le paquet statique de test existe ; **aucune URL publique fonctionnelle n'a été créée**. Sites n'expose pas d'outil dans cette session. L'aperçu Cloudflare gratuit a été autorisé par l'utilisateur, mais son API de provisionnement renvoie HTTP 403, « Your request was blocked ».

Ce bilan relit sources, reçus et limites, refait le profil mémoire du binaire actuel, vérifie les extensions PHP dans Chromium et relance les 35 tests Node. Il ne recompile pas les moteurs et ne présente pas toutes les anciennes suites navigateur comme réexécutées à ce jalon.

Pile épinglée : PHP 8.4.27, Emscripten 6.0.6 et lite4mariadb au commit `24be9371a2f6c71250a2356631ad6feab2280b02`. Les sources et l'en-tête généré de la compilation SQL annoncent **MariaDB 13.1.0, maturité alpha**. C'est un socle de prototype reproductible, pas une validation de production sur une release SQL finale ; la stratégie de maintenance/portage vers une base stable compatible doit être définie avant une diffusion large.

Le routage actuel sert les fichiers et les entrées PHP usuelles ; interpréter `.htaccess`, reproduire les réécritures Apache et couvrir les front controllers de frameworks restent à réaliser/valider. Un fichier `.htaccess` présent dans l'explorateur n'est pas une configuration Apache appliquée. L'installation automatique de dépendances Composer, les gros arbres `vendor/`, les processus système et des applications/frameworks complets ne doivent pas être présentés comme pris en charge sur la base des fixtures scolaires.

## Inventaire PHP : un manque important

Le moteur exécuté annonce : `Core`, `PDO`, `Reflection`, `SPL`, `date`, `hash`, `json`, `mysqli`, `pbl_native`, `pcre`, `pdo_mysql`, `random`, `session`, `standard`. Le seul driver PDO annoncé est `mysql`.

Absences confirmées dans le navigateur : `filter_var`, `ctype_alpha`, `mb_strlen`, `iconv`, `curl_init`, `imagecreate`, `token_get_all`, `finfo_open`, `gzencode`, ainsi que `ZipArchive`, `DOMDocument` et `SimpleXMLElement`. OpenSSL ne figure pas non plus dans les extensions chargées. La liste d'extensions du socle visé dans BUILD.md est une cible ; elle n'est pas la description du binaire minimal présent.

**Ajouter les extensions nécessaires aux applications usuelles est prioritaire.** Le coût doit être mesuré par groupe, notamment pour XML, ZIP/zlib, multioctets et images. Le ZIP de l'interface est traité en JavaScript : il ne prouve pas la disponibilité de ZIP dans PHP. Un wrapper FTP peut être enregistré sans que les sockets nécessaires fonctionnent dans le navigateur.

Preuve : `engine/fusion/receipts/php-inventory.json`. Reproduction : `node benchmarks/native/php-inventory.mjs` avec Playwright et ses navigateurs déjà installés.

## Compatibilité MySQLi restant à ajouter

Les 34 absences procédurales de l'inventaire PHP 8.4.27 se répartissent ainsi :

| Groupe | Entrées absentes |
|---|---|
| Connexion / options | change_user, connect_errno, connect_error, get_charset, options, set_opt, ssl_set |
| Requêtes / résultats | real_query, store_result, use_result, multi_query, more_results, next_result |
| Transactions | savepoint, release_savepoint |
| Statements | stmt_attr_get, stmt_attr_set, stmt_error_list, stmt_get_warnings, stmt_more_results, stmt_next_result, stmt_send_long_data |
| Diagnostics | error_list, get_warnings, stat, debug, dump_debug_info |
| Administration | kill, refresh |
| Asynchrone | poll, reap_async_query |
| Statistiques mysqlnd | get_client_stats, get_connection_stats, get_links_stats |

Chaque nom est préfixé par `mysqli_`. Les variantes objet et propriétés sont inventoriées séparément dans `packages/php-native/compatibility-inventory.json`. Prioriser les chemins courants : options, résultats multiples, long-data, savepoints, diagnostics et attributs. Pour TLS/sockets distants, asynchrone et statistiques propres à mysqlnd, définir ce qui est applicable au serveur embarqué ; ne pas simuler une réussite pour augmenter un compteur.

## Éditeur à terminer

L'éditeur actuel lit/écrit les vrais fichiers et conserve brouillon/sélection ; il reste un textarea. L'orientation demandée est enregistrée : **CodeMirror 6 + services WASM php-lsp et SuperHTML + SWC ou Babel-light**, avec définitions jQuery internes invisibles dans l'explorateur et les exports, sans injection de jQuery à l'exécution.

À réaliser : épingler les bons projets/versions, prototype WASM de langage, coloration et documents mixtes PHP/HTML/CSS/JS, complétion/diagnostics, résolution réelle des déclarations `.d.ts`, recherche/remplacement et navigation de fichiers, annulation des analyses périmées, plafonds de documents/index, arrêt/restauration des services. SWC/Babel seuls ne fournissent pas une résolution de types complète.

Il faut aussi protéger l'édition : détection des fichiers binaires et encodages, lecture seule appropriée, confirmation de perte d'un brouillon, opérations arborescentes et restauration du focus. L'intégration ne doit pas charger les services lourds au lancement de tous les projets.

## Mémoire : acquis, consommation et limites

Trois grandeurs distinctes : capacité de la mémoire linéaire WASM, occupation de son allocateur C, RAM globale PSS du navigateur. La capacité 256 Mio n'est pas une consommation totale de 256 Mio. Les buffers VFS JavaScript, copies, code compilé et processus navigateur ont un coût propre.

Le [rapport des profils](PROFILS-PERFORMANCE.md) conserve tous les chiffres et la recommandation. Mesure refaite sur le binaire actuel :

| Mode | Capacité WASM | PSS Chromium | PSS Firefox |
|---|---:|---:|---:|
| PHP seul, SQL non initialisée | 256 Mio | 278,93 Mio | 617,85 Mio |
| PHP + MariaDB, travail SQL du protocole | 256 Mio | 542,41 Mio | 758,26 Mio |

Le tas C occupé au stade SQL vaut environ 74,78 Mio. Une mesure après une requête PHP ne mesure pas son pic pendant l'exécution. Ces passages sont ponctuels ; aucune borne globale de 300 Mio n'est démontrée avec SQL actif.

Une fuite réelle de ~16,6 Mo par résultat excessif refusé a été corrigée : l'allocateur de lignes n'était pas libéré sur le chemin d'erreur. Dans le scénario de six refus, delta 0 console sur les deux navigateurs, 16 octets PDO Chromium / 0 Firefox après échauffement. La preuve d'endurance longue reste ouverte.

Principales limites appliquées :

| Ressource | Borne actuelle |
|---|---:|
| Mémoire linéaire du module | initiale 256 Mio, maximum 512 Mio |
| Connexions SQL appelantes | 32 |
| Handles préparés natifs PDO/MySQLi partagés | 128 |
| Texte SQL préparé réservé / requête SQL | 16 Mio cumulés / 8 Mio par commande |
| Résultat SQL | budget de blocs 16 Mio, 10 000 lignes |
| VFS projet / SQL / temporaire / repli | 64 / 128 / 16 / 16 Mio logiques |
| Fichier projet / fichier SQL | 16 / 64 Mio |
| Fichiers ouverts | 512 |
| HTTP PHP sortant : requête / réponse | 8 / 16 Mio |
| Sortie d'une requête PHP vers l'hôte | 8 Mio |
| RPC en attente / file Worker | 64 appels / 32 tâches, 8 Mio de données comptées |
| Journal | 200 événements, messages/détails/récupération bornés |

Le stockage SQL initial occupe déjà environ 63 Mio logiques : le quota SQL de 128 Mio n'est pas 128 Mio de données utilisateur disponibles. Les quotas de fichiers ne sont pas une égalité de RAM. Les allocations de travail SQL, paramètres volumineux, index, tris/jointures, surallocations et buffers internes du navigateur demandent encore une analyse et des garde-fous.

## Ce qui manque : ordre conseillé

| Priorité | Nature | Livrable concret / condition de sortie |
|---|---|---|
| 1 | Ajout / livraison | Publier le paquet sur un hébergement accessible avec les bons en-têtes, obtenir une vraie URL et vérifier ouverture du projet + client PHP + sauvegarde |
| 2 | Compatibilité | Compléter les extensions PHP usuelles nécessaires ; faire passer plusieurs petits projets réellement importés et inchangés, avec dépendances identifiées |
| 3 | Compatibilité native | Étendre MySQLi par lots utiles et fixer la matrice PDO types/attributs/curseurs/erreurs ; chaque lot livre une fonctionnalité et un parcours réel ciblé |
| 4 | Ajout éditeur | CodeMirror d'abord, puis service PHP/HTML et complétion jQuery démontrée ; mémoire et déchargement mesurés |
| 5 | Finalisation SQL | Formulaires de schéma/index/colonnes, filtres/tri/recherche, multi-résultats, import DELIMITER, erreurs locales et sauvegarde/restauration globale |
| 6 | Robustesse | Disque plein InnoDB/IndexedDB, démarrage SQL interrompu, migration legacy, sauvegarde fichiers + toutes les bases, fermeture/crash sous charge |
| 7 | Optimisation | Mémoire initiale 64/128 Mio à éprouver, threads internes SQL avant réduction du pool, pics/plateaux sur longue durée, coût des outils et comparaison reproductible aux témoins |
| 8 | Finition produit | Explorateur complet, focus et navigation, lecteurs d'écran/Safari, état des modifications, messages cohérents, guide et recettes de build/distribution de la version courante |

À inclure dans la robustesse : annulation et délais des longues requêtes PHP/SQL. Le runtime actuel laisse `max_execution_time=0` côté PHP ; le watchdog de l'API hôte finit par détruire le Worker à expiration d'un appel, pas par annuler proprement une seule requête. L'interface ne propose pas encore un contrôle fin de pause/annulation. Ajouter aussi un choix explicite de préchauffage SQL par projet si nécessaire ; le comportement livré reste l'activation automatique au premier besoin.

Pour la finalisation technique : documenter la maintenance du fork SQL alpha, les recettes de reconstruction propre et les versions réellement livrées. Une mise à jour de version doit conserver les correctifs natifs et repasser les parcours concernés ; elle n'est pas une simple modification d'un numéro dans un manifeste.

Ce séquencement n'impose pas d'attendre un audit exhaustif avant chaque fonctionnalité. Alterner une avancée visible/native et sa vérification ciblée, puis consolider à chaque jalon. Les priorités de compatibilité, éditeur et SQL peuvent être découpées en incréments courts sans relancer les témoins amont à chaque modification.

## Optimisations conseillées et décisions à conserver

1. Conserver **le profil réduit actuel et SQL à la demande**, choisir Chromium pour les premiers essais sur machine limitée selon les consommations mesurées ; maintenir Firefox comme cible fonctionnelle.
2. Conserver 16 Workers autorisés après activation pour l'instant : le pic observé est 15. Pour descendre, mesurer une réduction des threads I/O/purge InnoDB avant d'abaisser le pool. Ne pas choisir 8 sans preuve.
3. Étudier une capacité initiale WASM de 64/128 Mio avec tests de croissance partagée, pointeurs/vues, imports et concurrence ; aucune économie chiffrée de ces variantes n'est encore acquise.
4. Charger les services d'édition au premier besoin, séparer leur cycle de vie du moteur, borner index, documents et requêtes d'analyse. Mesurer le DOM et les modèles réellement libérés au déchargement.
5. Mesurer pics et plateau, avec/sans SQL et avec/sans outils, sur plusieurs projets et longues sessions. Les mesures immédiatement après stop/destruction ne prouvent pas une restitution de RAM.
   Compléter par CPU, coût énergétique, transfert HTTP réellement compressé et comparaison aux témoins avec le même protocole ; ces consommations ne sont pas encore instrumentées dans les profils disponibles.
6. Garder snapshots explicites et nouveau moteur après arrêt SQL. La première activation fonctionne sans redémarrage et sans rejeu ; l'arrêt/redémarrage MariaDB dans un même WASM a été abandonné après un abort reproduit.

Les profils « web statique sans WASM », « SQL compact », « SQL capacité accrue » et « édition complète » restent à construire/mesurer. Il serait trompeur de leur attribuer aujourd'hui un budget ou un débit garanti.

## Preuves et ce qu'elles ne prouvent pas

- **Maintenant :** 35 tests Node passent ; profil mémoire actuel et inventaire PHP refaits dans le navigateur. JSON archivés avec le bilan.
- **Jalons précédents conservés :** compilation native, compatibilité et quotas, HTTP borné, erreurs/transactions/snapshots sur Chromium/Firefox ; quatre fenêtres/trois sessions, grille, schéma et export/restauration ; package actuel PHP/PDO/MySQLi et POST sans rejeu sur les deux navigateurs.
- **Interface :** 17 états inspectés par axe-core dans Chromium, zéro violation automatisée détectée ; largeurs 320/768/1440 et texte 200 % vérifiés ; pas de certification WCAG ni d'annonces NVDA/VoiceOver validées.
- **Charge courte :** deux clients, 5 puis 10 requêtes/s offertes par client, 10 secondes par palier, réponses et compteurs vérifiés. Ce n'est pas le débit maximal ni une preuve d'endurance à N fenêtres.
- **Publication :** paquet prêt, pas de site public confirmé. La publication de l'environnement cloud ne publie pas cette application.

L'accès direct aux dossiers du PC, le réseau entre appareils et la compatibilité WordPress étendue restent hors du premier prototype. L'isolation virtuelle actuelle ne constitue pas une frontière de sécurité entre projets JavaScript hostiles ; une isolation par origines réelles et une couverture plus large des API navigateur restent à arbitrer.
